## 5. The project chat (CHAT)

The chat is how a person gets into, runs and understands a project. It MUST meet the bar of the best coding-assistant chats: fast, streaming, keyboard-first and honest about what is happening. Every other view is one step away from it, never instead of it.

- **CHAT-1 Front door.** Creating a project starts a chat with the Founder, and that same conversation becomes the project chat after creation. Opening a project opens its chat. Plan, board, deliverables, budget, memory and settings open as panels beside it, or as commands in it. The same chat is reachable from the app, the terminal (`crewmind chat`), the project's Slack channel and MCP.
- **CHAT-2 Talk to anyone.** Messages go to the CEO by default. `@name` addresses any agent in the project, and `@team` addresses a team's lead. The addressed agent answers in the thread as itself. Agents other than the CEO post in the project chat only when addressed or when replying in a thread they were addressed in (MSG-2). The CEO sees every conversation in its project; there are no side channels.
- **CHAT-3 Never silent.** A sent message shows as delivered within 1 second. While an agent works, the chat shows a live line of what it is doing ("reading the plan", "running the check on task 14"). On a warm chat, first words stream within 5 seconds. If no reply can start within 60 seconds, the platform posts a status naming the reason and when a reply will come, at 0 tokens. Reasons include a limit, the budget wall, a provider outage, a crash being retried, or a held project.
- **CHAT-4 Composer.** Multi-line markdown input. Slash commands with autocomplete. `@` mentions for agents, teams, artifacts, requirements and tasks. Attach files and images by drag-and-drop, paste or picker. Up-arrow history. Edit and resend the last message. Esc interrupts a reply in progress. A command palette and full keyboard use. After an interrupt the chat says the reply was stopped, and that reply does not start again by itself; the next message is answered as usual.
- **CHAT-5 Slash commands.** At minimum: `/do`, `/pin`, `/unpin`, `/decide`, `/fix`, `/example`, `/grill`, `/hold [until <time>]`, `/resume`, `/stop`, `/status`, `/plan`, `/deliverables`, `/desk`, `/budget`, `/quality`, `/brevity`, `/lock`, `/help`. Each is an operation in the catalog (IF-1.1), so the CLI, MCP and Slack offer it too.
- **CHAT-6 Conversation versus command.** Plain messages are conversation: agents answer, explain, propose and ask. A chat run changes no state except posting, writing its own memory notes, and carrying out a directive it cites (MSG-3, INV-23). Work runs act on the agent's own plan within its authority without asking.
- **CHAT-7 Action cards.** When an agent wants to act on something said in chat, it posts a card: what it will do, its estimated tokens, and whether it can be undone. Buttons are Do it / Not now / Edit. "Do it" creates a directive. One tap, no retyping.
- **CHAT-8 Pin, decide, fix, example.** Any chairman message can be pinned as a standing order, turned into a closed decision, or marked as an example, by command or by a button on the message. Any agent message can be marked "Not what I asked" (`/fix`). Sections MSG-4 to MSG-7 define the effects.
- **CHAT-9 Uploads.** Files and images up to `upload.max_size` \[100 MB\] each become artifacts of kind upload. They appear in the chat as previews, are readable by every agent in the project, and are treated as untrusted input (P4). Seats on vision-capable models receive images directly. For other seats, the platform has a vision-capable seat describe the image once, metered, and caches the description. The chairman can mark an upload as **reference** (a binding source) or **example** (illustrative only). An upload's line in the chat is not a question: it starts no reply and costs no tokens (P8).
- **CHAT-10 Rich rendering.** Markdown, highlighted code, tables, diffs, images, and previews of artifacts (CHAT-16). Decision items appear as cards with their typed actions; plans and runs as progress cards. Long agent content folds behind "details" (P18).
- **CHAT-11 Answer the question asked.** Every agent reply to the chairman is threaded to the message it answers. The chairman's newest unanswered message is always first in the agent's context (MSG-10). After a `/fix`, the agent's next reply quotes the original question before answering it.
- **CHAT-12 Listening score.** Each agent's corrections per 100 replies is shown on its seat card, in the daily brief, and in the run health report. A rising score is a flag (HUM-6).
- **CHAT-13 Brevity.** `/brevity` sets `chat.brevity` \[normal\] to short, normal or detailed, per person. The communication standard (MSG-12) applies at every setting.
- **CHAT-14 Threads and search.** Threads per topic. Full-text search across the project's history, artifacts and memory. Any message links to the run and trace that produced it.
- **CHAT-15 Since you were away.** When the chairman opens the chat after `brief.away_after` \[4 h\], the chat starts with a summary built at 0 tokens from the event log. It covers what moved, what decided itself, what waits on them, and what happens next.
- **CHAT-16 Artifact previews.** Markdown, PDF, images, CSV and spreadsheets as tables, code, audio and video play inline. HTML renders in a sandboxed frame with no network. Every version can be downloaded; text versions can be compared side by side.
- **CHAT-17 Multi-person.** Co-chairs post as themselves; observers read. Each person has their own read position, snoozes and notification settings.
- **CHAT-18 Always-visible header.** **Now** (what each active agent is doing), **Next** (the next wakes and deadlines, from the agenda), **Waiting on you** (the desk count), and the budget used against the wall. Each item opens its panel.
- **CHAT-19 Activity feed.** A collapsible feed beside the chat shows every state change in plain words, each linked to the requirement or bet it serves. Holds show their reason and lift time (EXE-4).
- **CHAT-20 Everywhere.** The chat works on phone browsers (responsive, installable as a web app with push notifications for alarms), in the terminal (IF-4.8) and in Slack (INT-5).
  - A person turns push alerts on per browser. The server accepts a push subscription only when its address is an https address at a browser push service (Google, Mozilla, Apple, Microsoft); any other address is refused, so a subscription cannot make the server post elsewhere.
  - The install signs its pushes with one key pair. The private half is a secret (INV-6); only the public half is shown.
  - An alarm is queued in the change that causes it and sent afterwards, once per browser of each project member. The push service holds it for up to 24 hours. A subscription the push service reports as gone is deleted.
  - A pause the platform makes (budget wall, credential failures, skipped cycles) is an alarm. A hold the chairman sets is not.
