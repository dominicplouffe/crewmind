# API proposals

The redesign uses only what the server already returns. Where the brief asked for more, the UI shows the honest version and the data it would need is proposed here. Nothing below is built; each is a proposal for the owner. None changes a rule.

| # | Proposal | Why the UI wants it | Shape | Spec impact |
| --- | --- | --- | --- | --- |
| A-1 | **Money beside tokens** | The brief asks for budgets "in money and time as well as tokens". Budgets are tokens only (revision 2, GOV-2), so the UI shows tokens and time, never an invented price. | `GET /v1/budget/show` gains `estimate: {currency, spent, wall, per_million_input, per_million_output, source: "provider list price", as_of}` per credential lineup, computed at the gateway from LiteLLM's price map. Labelled "estimate at list price". | New read-only field; P12 (honest substitutions) requires the label. No rule. |
| A-2 | **Display names for agents** | Agents are shown by seat name ("CEO", "writer-1") and role. A person-like name ("Maya, CEO") reads warmer in timelines. | Seat gains optional `display_name` chosen at hire from a name list in the squad definition; mentions still use the seat name. | LIB-2 squad field; seat table column. Optional. |
| A-3 | **What each agent is doing, in words** | `chat.header.now[].doing` is "thinking", "using a tool", "starting". The squad view would say "Writing landing-copy.md for requirement 2". | `now[]` gains `task_id`, `task_title`, `requirement_id` and, for tool calls, a plain tool label from the catalog (never raw arguments: P4). | Read-only; built from the run's current task. |
| A-4 | **Per-agent totals** | The squad view sums `tokens_counted` from `runs.list`, which pages. A long project needs a total per seat without paging every run. | `GET /v1/roster/show` seats gain `tokens_total`, `runs_total`, `last_active_at`. | Read model over the ledger (P9). |
| A-5 | **Projected finish date and spend together** | `plan.show.pace` has `projected_at` and `projected_spend`; the burn chart joins them with `budget.show`. One call would avoid two reads that can disagree for a moment. | `GET /v1/plan/show` `pace` gains `wall`, `spent`, and `lasts_until` (when the budget runs out at the current burn rate). | Read-only. |
| A-6 | **"Discuss" goes to the card's message** | A decision on Home links to the project chat, not to the card's message. | `DeskEntry.item` gains `message_id` (the chat line that carries the card). | Read-only. |
| A-7 | **Feed lines name settings in words** | Activity lines for setting changes come from the server with the setting's key ("run.timeout changed from 5400 to 3600"). The web rewrites them with its labels; other surfaces (CLI, Slack) still show keys. | The registry gains `label` and `display_unit` per setting (Appendix A gains two columns), and `record.feed` uses them. | Appendix A columns; a test that every setting has a label. |
| A-8 | **Who holds a decision** | The plan shows who must act on a requirement (you, the CEO or the reviewer) by reading the desk. The plan view could say it directly. | `RequirementItem` gains `decided_by: "chairman" \| "ceo" \| "reviewer" \| null` from the authority settings. | Read-only (GOV-1). |
| A-9 | **A cross-project squad view** | The brief's IA suggests "Squad" as a global place. Seats belong to one project, so Squad is a project tab. | `GET /v1/roster/mine` listing seats across the person's projects with status. | Read-only. Only if the owner wants a global Squad place. |
| A-10 | **Newest first for runs and the feed** | The squad view and the Overview timeline page from the oldest item to find the latest (capped at 4,000 runs and 20 feed pages). | `order=desc` (or `before`) on `runs.list` and `record.feed`. | Read-only. |
| A-11 | **Who filed a decision item** | `filed_by` is "agent" or "platform", so the card infers "The CEO asks" from the item kind. | `ItemView.filed_by_seat` (seat name, or null for the platform). | Read-only. |
| A-12 | **Change your own name** | The seeded admin is called "Admin" and there is no way to rename oneself, so Profile is read-only. | `people.rename_me {name}` (an operation on every surface, IF-1). | New operation, small. |
| A-13 | **Typed settings registry** | The web parses each setting's `allowed` text ("10–360 min") to build controls. | `settings.registry` items gain `kind`, `min`, `max`, `choices`, `unit`. | Appendix A columns; same as A-7. |
| A-14 | **`founder.credential` names a real key** | The setting accepts any text, so a typo leaves the Founder silently unset until the first drafting turn fails. | Refuse a value that is not the name of an active model credential (a constraint in Appendix A). | A new refusal (P1); needs an attack test. Flagged for the owner, not built. |
| A-15 | **Who added each key** | Admins see keys without their owner. | `CredentialItem.owner_name`. | Read-only. |
| A-16 | **Member-visible admin names** | `people.list` is admin-only, so a member is told "ask an admin" without a name. | `people.admins` returning names only. | Read-only. |
| A-17 | **A test call for mock keys** | The key test fails on the mock provider ("LLM Provider NOT provided"), so first-run setup on a test install offers "Keep it anyway". | Let `credentials.smoke` answer for the mock provider. | Test installs only. |
| A-18 | **Decision item with its chat message** (no longer needed: the web loads `items.list` once and seeds every card) | A decision card in the chat loads its item after the message renders, so it grows in place and pushes the messages below (layout shift 0.08–0.18 on a slow phone). | `MessageItem.detail` for a decision item carries the `ItemView`, as `desk.show` already does. | Read-only. |
| A-19 | **Structured feed items** | The Overview's timeline reads subject ids and states out of the server's sentences ("Task 4 is now done.") to name tasks and hide noise. | `FeedItem` gains `subject_kind`, `subject_id`, `before_state`, `after_state`, `actor_name`, `actor_kind`. Names of agent-written subjects (task titles) stay out of the feed's text: they are agent text and must reach an AI client wrapped as untrusted (INV-7), so the web looks them up itself. | Read-only. |
| A-20 | **Chairman-relevant feed** | Lines such as "Chat session 1 is now warm" are bookkeeping. | A `for_chairman` flag (or a filtered view) on `record.feed`. | Read-only. |
